# Route: T3 Code

Ground truth: the installed T3 Code — the running app's schema is the authority on command shape.

## Dispatch

Run the bundled helper with the resolved provider instance, current model, and prepared directory:

    scripts/t3-thread.py --name "<name>" --prompt "<prompt>" \
      --project-directory <project-root> --directory <directory> --branch <branch> \
      --provider <codex-or-claude-instance> --model <model> --effort <effort> \
      --runtime-mode <mode>

`--project-directory` takes the registered project root and `--directory` the working directory — distinct values when dispatching into a worktree.

The helper discovers the local runtime and installed server CLI, requires a loopback HTTP origin, resolves the active project by its registered root, and sends `thread.create` then `thread.turn.start`. It registers a supplied external worktree path and branch; T3 supervises the conversation but does not create or clean the worktree. Creation omits the automatic title seed so the supplied name remains stable.

`--runtime-mode` takes T3's own runtime modes — currently `approval-required`, `auto-accept-edits`, `auto`, or `full-access` — never a provider sandbox name like `workspace-write`; the app refuses anything outside its schema.

## Instance-id validation — liveness before success

`--provider` names a provider instance id the running app must recognize. The app accepts `thread.create` and `thread.turn.start` with an unknown instance id and only fails the turn async in-app, after the helper has already exited zero — so the helper's exit alone does not fail fast. Close the gap on one side or the other:

- **Before create:** validate the supplied instance id against the app's known provider instances — the shell snapshot the helper reads at `/api/orchestration/shell` lists them; an id the app does not list fails the dispatch here, at the command line.
- **Or immediately after start:** verify the turn's state — the named thread shows its turn actually running, not created-then-dead. A turn that died at start is a failed dispatch, reported now, never left for the user to discover in the sidebar.

Turn-state verification is provider-asymmetric (probed 2026-08-24, T3 Code (Alpha) 0.0.33). codex surfaces a dead turn honestly: state `error`, `session.lastError` set. claudeAgent completes it: a model the gateway rejects yields turn state `completed`, session `ready`, and the provider error as the assistant reply text (`API Error: 400 unknown provider for model …`). Verifying a claudeAgent spawn therefore means reading the first assistant message — the thread's provider event log at `~/.t3/userdata/logs/provider/events.<threadId>.log` carries it, and its `session.configured` line shows the resolved model and effort.

## Model options — probed 2026-08-24, T3 Code (Alpha) 0.0.33

- Each driver reads one effort option id — claudeAgent `effort`, codex `reasoningEffort` — and ignores every other id, silently running the thread at its default effort. The helper maps the id from the instance id; pass `--effort-option-id` for an instance under another name.
- Both drivers take effort values `low`, `medium`, `high`, `xhigh`, `max`. codex fails the turn on anything else and names that list; claudeAgent coerces an unknown value to its default (`high`) and omits effort for models without it.
- The gateway serves claude-fable-5, claude-opus-5, claude-sonnet-5 (fable and opus resolve to their `[1m]` context variants) and gpt-5.6-sol, gpt-5.6-luna, gpt-5.6-terra. Any other model — haiku and older opus included — reaches the provider and fails there with `unknown provider for model …`, surfacing per the asymmetry above.

## Runtime discovery off the macOS bundle

The helper's automatic discovery assumes the macOS desktop bundle under `/Applications`. On Linux, T3 runs as a Node CLI and that discovery fails — pass `--t3-executable` and `--server-entry` explicitly.

## Failure handling

A payload the app rejects at schema decode comes back as HTTP 400 with an empty body, and the helper degrades that into a capability-drift report: which command was refused, the values it sent, the enum sets the last probed app accepted when the refused command carries those fields, and where to re-probe. Any create the app refuses outright — any 4xx, the empty-body schema rejection included — was never applied, so the helper skips the compensating delete instead of manufacturing a second failure. If turn start fails after creation, the helper deletes the partial thread; when that delete itself fails, the error names the orphaned thread id and title and tells the user to discard it from the T3 sidebar.

A missing local project, a command the app's schema refuses, authentication failure, or a non-local origin is capability drift: report it and stop before falling through to the provider harness. Remote servers and custom T3 homes are unsupported.

## Report

Tell the user to open the named thread in the T3 project sidebar.
