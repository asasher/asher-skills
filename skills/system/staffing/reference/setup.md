# Setup — a template fill

Write or reconcile the project's staffing playbook — the sole authority for the roster — and the trigger that makes sessions read it. Setup writes only inside the repo. There are no probes, no overlay, and no machine stamps: reachability is discovered at the point of use, not recorded here.

1. Read the existing playbook (the staffing file under the repo's agent-docs directory) if there is one, and the bundled [roster seed](../templates/roster-seed.md). The seed supplies starting values for the judgment numbers — cost, intelligence, taste, effort — because those cannot be derived; it is read here and never at resolution time.
2. Run a short **repo-deltas interview**: which models the owner wants excluded or added, cost sensitivities, pins to keep or change (e.g. mechanical/bulk → a named worker route), which surfaces here are user-facing and so carry the hard taste bar, and which capability routes this repo needs declared (browser, computer use, imagegen — the provider that supplies each, plus any fallback).
3. Write or reconcile the playbook: a roster table with the judgment numbers, the pins, the declared capability routes, and the repo deltas — roughly twenty lines. It is repo-owned: reconcile an existing file clause by clause, never overwrite it wholesale, and owner-tuned judgment numbers always survive a re-run. The playbook carries **data only** — a playbook that restates a resolution rule or a command shape has copied something that will drift; doctrine stays in this skill's references.
4. Reconcile the shipped trigger template (`templates/instruction-trigger.md`) into the project's agent instruction file — the harness-neutral base every harness loads where one exists, else the instruction file the repo's harnesses actually read. A playbook nothing points at is never consulted. Reconcile an existing § Staffing section to the template's content — a section already matching it is left as it is; never overwrite foreign sections.

Completion criterion: the project resolves an unambiguous roster from its playbook alone — no home-directory dependency, no runtime read of the seed, and no recorded machine state anywhere. A re-run that changes no answer leaves the file byte-identical.
