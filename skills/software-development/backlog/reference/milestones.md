# Milestone batches

Use a repository milestone to group a requested batch, such as findings from one user-testing session. Keep one ticket per distinct problem. The milestone description holds shared context and source links; each ticket carries enough evidence to stand alone.

Milestone membership organizes progress. Readiness, native blockers, and approved spec splits determine execution and branches. A spec parent and its implementation children can all belong to the same milestone.

## Capture and split

Reuse the named milestone, or propose its title and description alongside the issue drafts. Create and assign it within the user's approved capture plan. A due date is optional. Read back assignments with the tickets.

When splitting a ticket or adding work under a spec parent, inherit its milestone. GitHub permits one milestone per issue: include any conflicting assignment in the plan for the user's decision. Keep existing assignments until a replacement is approved.

## Groom and completion

Preserve milestone membership when consolidating tickets. For findings from different milestones, propose the survivor's assignment and link it from the other milestone descriptions, keeping outstanding work visible after duplicates close.

Review the milestone's open and closed items and any linked replacement work before proposing closure. An empty milestone or all-closed counter alone does not establish completion: account for duplicates, moved work, and exclusions. Groom includes milestone closure in its approved plan; status reports candidates. Read back authorized closures.

## Existing grouping issues

For a requested migration, propose the milestone, child assignments, and transfer of shared context. Retire organizational parent links and their grouping-only blockers after readback; preserve true dependencies and approved spec parentage. Close the old grouping issue with a milestone link after the user approves the migration. Ordinary capture leaves existing groupings intact unless migration is selected.
