3. **P3 — Do not publish yet.** My judgment is insufficient; present the complete draft and quiz the user about granularity and blocking edges. Publish only after they approve that draft.

4. **P4 — Stop before publishing.** State that no tracker binding is recorded and ask the user how to proceed.

   > “No recorded binding at all: state the gap and ask the user how to proceed — a backlog needs a tracker, so publishing waits on that decision.”

5. **P5 — Leave readiness unset by default.** Split approval does not automatically apply readiness. Apply it only if the user also asks to bless the tickets for pickup.

   > “Do **not** auto-apply the readiness role on a fresh split — drafted work is not yet blessed for pickup.”  
   > — `to-slices/reference/slicing.md`

   > “**Note the option** to apply readiness on approval — the quiz *is* a human confirmation, so a user who wants it may bless the tickets on the spot — but absent that request, leave readiness unset.”  
   > — `to-slices/reference/slicing.md`

6. **P6 — Create blockers first and use GitHub’s native `blocked_by` relation.** Topologically sort the tickets so every blocker receives an ID before its dependents, then write the native edges recorded by the playbooks.

   > “Once the split is approved, sort the tickets into **dependency order — blockers first.**”

   > “Where the playbook records the tracker's **native blocking relation** (e.g. GitHub `blocked_by`, written via the verbs in `docs/agents/platform.md`), write the native edge — it renders the blocking structure in the tracker's own UI.”

   > “**Attach every slice as a child** of the parent, through the parent/child relation the platform playbook records (`docs/agents/platform.md` — the tracker's native sub-issue relation where it has one, else the playbook's recorded form).”

   > “The parent's spec text is never edited, and its readiness role is left as it stands — the open-children rule, not a label change, is what keeps it out of the build sweep.”
